## Опис реалізації

Проєкт реалізує повноцінний вебсервіс реєстру пристроїв (Device Registry API) на базі маршрутизатора Chi для централізованого обліку фізичних та віртуальних вузлів мережі:

### 1. Шарувата архітектура проєкту:
- internal/domain:
  - Device — сутність пристрою (id, name, ip_address, type, status, updated_at).
  - CreateDeviceRequest, UpdateDeviceRequest — DTO для створення та оновлення.
  - DeviceFilter — параметри для фільтрації за статусом та типом.
  - ErrorResponse — уніфікована структура помилки (RFC 7807).
- internal/repository:
  - DeviceRepository — інтерфейс операцій зі сховищем.
  - MemoryDeviceRepository — потокобезпечна in-memory реалізація на базі карти map[string]domain.Device із розмежуванням блокувань через sync.RWMutex (RLock для читання, Lock для запису).
- internal/handler:
  - DeviceHandler — контролер HTTP-запитів із методами ListDevices, GetDevice, CreateDevice, UpdateDevice, DeleteDevice.
- internal/middleware:
  - LoggerMiddleware — вимірює тривалість запиту та логує метод, шлях, статус-код, час і IP клієнта.
  - RecovererMiddleware — перехоплює паніки через recover(), виводить стек-трейс та повертає клієнту відповідь 500 Internal Server Error.
  - CORSMiddleware — додає заголовки міждоменного доступу (Access-Control-Allow-Origin: *, методи, заголовки, обробка OPTIONS).

### 2. Реалізовані рівні функціональності:
- Рівень 1 (Базовий): шарувата структура, сховище з RWMutex, створення пристрою (POST 201 Created), отримання списку (GET 200 OK), пошук за ID (GET 200 OK / 404 Not Found).
- Рівень 2 (Ключовий): повний цикл REST CRUD (PUT 200 OK / 404 Not Found, DELETE 204 No Content / 404 Not Found), підключення middleware логування.
- Рівень 3 (Просунутий): фільтрація за параметрами URL (?status=online&type=sensor), стандартизований формат JSON-помилок RFC 7807, захисний Panic Recoverer та налаштування CORS.

## Інструкція із запуску

### 1. Запуск сервера:
```powershell
cd C:\Users\denchik\Desktop\labs\Client-Server-Architecture\Lab-04

```
Сервер запуститься на порті :8080 (можна змінити прапорцем: `go run . -port 8080`).

### 2. Приклади тестування API через cURL:

**Створення нового пристрою (POST):**
```powershell
curl.exe -i -X POST http://localhost:8080/api/v1/devices `
  -H "Content-Type: application/json" `
  -d "{\"name\":\"Main Thermal Sensor\",\"ip_address\":\"192.168.1.50\",\"type\":\"sensor\",\"status\":\"online\"}"
```

**Отримання списку пристроїв із фільтрацією (GET):**
```powershell
curl.exe -i "http://localhost:8080/api/v1/devices?status=online&type=sensor"
```

**Отримання конкретного пристрою за ID (GET):**
```powershell
curl.exe -i http://localhost:8080/api/v1/devices/dev-001
```

**Оновлення пристрою (PUT):**
```powershell
curl.exe -i -X PUT http://localhost:8080/api/v1/devices/dev-001 `
  -H "Content-Type: application/json" `
  -d "{\"name\":\"Updated Thermal Sensor\",\"status\":\"offline\"}"
```

**Видалення пристрою (DELETE):**
```powershell
curl.exe -i -X DELETE http://localhost:8080/api/v1/devices/dev-001
```

**Перевірка відповіді 404 Not Found:**
```powershell
curl.exe -i http://localhost:8080/api/v1/devices/unknown-device
```

## Відповіді на контрольні питання

### 1. Чим відрізняється архітектурний стиль REST від віддаленого виклику процедур (RPC) за принципами адресації та набором операцій?
- **REST (Representational State Transfer)**: орієнтований на ресурси (Resource-oriented). Адресація вказує на іменники — сутності системи (наприклад, `/devices/{id}`). Набір дій є фіксованим і універсальним для всіх ресурсів згідно зі стандартними HTTP-дієсловами (GET, POST, PUT, DELETE).
- **RPC (Remote Procedure Call)**: орієнтований на операції / методи (Action-oriented). Адресація вказує на назву викликаної процедури або функції (наприклад, `/createDevice`, `/getDeviceById`, `/deleteDevice`). Набір операцій не обмежений і є специфічним для кожного сервісу.

### 2. У чому полягає відмінність між безпечними (safe) та ідемпотентними (idempotent) HTTP-методами? До якої категорії належать методи GET, POST, PUT, DELETE?
- **Безпечні методи (Safe)**: операції, виконання яких лише читає стан і не призводить до будь-яких мутацій даних на сервері.
- **Ідемпотентні методи (Idempotent)**: операції, повторний виклик яких із тими самими параметрами один або декілька разів призводить до однакового кінцевого стану ресурсу на сервері.

Категоризація методів:
- **GET**: Безпечний (Safe) та Ідемпотентний (Idempotent). Повторні запити повертають ті самі дані і не змінюють ресурси.
- **POST**: Небезпечний (Unsafe) та Неідемпотентний (Non-idempotent). Повторне надсилання призведе до створення декількох дублюючих ресурсів із різними ID.
- **PUT**: Небезпечний (Unsafe), але Ідемпотентний (Idempotent). Багаторазова заміна ресурсу за фіксованим ID приводить до одного й того самого фінального стану.
- **DELETE**: Небезпечний (Unsafe), але Ідемпотентний (Idempotent). Перше видалення знищує ресурс, повторні запити фіксують факт його відсутності (кінцевий стан ресурсу однаковий — він відсутній).

### 3. Які переваги надає маршрутизатор Chi над стандартним http.ServeMux при побудові комплексних API? Що таке дерево Radix Tree?
- **Переваги Chi**:
  - 100% сумісність зі стандартним інтерфейсом http.Handler (жодних специфічних сигнатур, легка переносимість).
  - Підтримка суб-роутерів та просторів імен (r.Route) для зручного версіонування API (`/api/v1`).
  - Проста та елегантна робота з динамічними параметрами URL (`{id}`) через `chi.URLParam`.
  - Зручна композиція конвеєрів Middleware (як глобальних, так і локальних для окремих піддерев маршрутів).
- **Radix Tree (стиснене префіксне дерево)**: структура даних, у якій спільні префікси рядків шляхів об'єднуються у спільні вузли. Завдяки цьому пошук маршруту виконується за час $O(k)$, де $k$ — довжина вхідного URL, незалежно від загальної кількості зареєстрованих ендпоінтів у додатку, забезпечуючи нульові витрати пам'яті (zero allocations) при співставленні шляху.

### 4. Чому для in-memory репозиторію у конкурентному вебсервері обов’язково використовувати sync.RWMutex, а не звичайний sync.Mutex або незахищену карту?
Стандартна карта Go (`map`) категорично не захищена від одночасного доступу. Якщо одна горутина читає мапу, а інша в цей момент записує в неї — Go аварійно завершує весь процес фатальною панікою `fatal error: concurrent map read and map write`.  
Звичайний `sync.Mutex` повністю блокує всі горутини, дозволяючи лише одному потоку оперувати даними одночасно. У реальних REST API частка операцій читання (GET) зазвичай сягає 80–95%. `sync.RWMutex` (м'ютекс читання-запису) дозволяє паралельно виконувати необмежену кількість операцій читання одночасно через `RLock()`, блокуючи доступ лише у момент ексклюзивного запису через `Lock()`, що значно підвищує пропускну здатність сервера.

### 5. У яких випадках повертається код стану 204 No Content, і чому в тілі такої відповіді заборонено передавати дані?
Код `204 No Content` повертається тоді, коли запит клієнта успішно виконано, але відповідь не повинна повертати жодного представлення сутності. Найчастіше це використовується при операціях `DELETE` (ресурс видалено, тіла немає) або `PUT`/`PATCH`, коли клієнту достатньо лише підтвердження успіху операції.  
Згідно зі специфікацією HTTP (RFC 9110), заголовок `204` прямо вказує клієнту і браузеру, що повідомлення завершується одразу після секції заголовків. Передача будь-яких байтів у тілі порушує специфікацію і може призвести до десинхронізації HTTP-пайплайну або помилок парсингу у клієнтських бібліотеках.

### 6. Як влаштований механізм передачі контексту керування в ланцюжку Middleware (next.ServeHTTP)?
Middleware у Go будується за шаблоном проектування Decorator / Chain of Responsibility. Middleware — це функція-обгортка, яка приймає `next http.Handler` і повертає новий `http.HandlerFunc`.  
Коли надходить HTTP-запит:
1. Виконується код Middleware до виклику `next.ServeHTTP(w, r)` (наприклад, фіксація часу старту `time.Now()`, перевірка токенів, встановлення CORS-заголовків);
2. Виклик `next.ServeHTTP(w, r)` передає керування наступному обробнику в конвеєрі або безпосередньо фінальному хендлеру ендпоінта;
3. Після повернення з `next.ServeHTTP` виконується пост-обробка (наприклад, замір тривалості `time.Since()`, логування або скидання метрик).

### 7. Як за допомогою вбудованої функції recover() організувати захист HTTP-сервера від падіння при виникненні паніки в одній із горутин-обробників?
Кожен HTTP-запит у Go стандартно обробляється в окремій горутині. Якщо в хендлері трапиться помилка розіменування нульового вказівника або вихід за межі масиву (паніка), без обробки вона завершить весь процес сервера.  
Захист організовується через Middleware із відкладеним викликом функції `defer`:
```go
defer func() {
    if err := recover(); err != nil {
        log.Printf("Panic: %v\n%s", err, debug.Stack())
        w.WriteHeader(http.StatusInternalServerError)
        // повернення клієнту стандартизованого 500 JSON
    }
}()
```
Функція `recover()` перехоплює аварійний стан паніки, переводить виконання в нормальний режим і дозволяє повернути клієнту стандартизований статус `500 Internal Server Error`, зберігаючи сервер працездатним для всіх інших клієнтів.

### 8. Що таке CORS і чому запити від вебклієнтів до REST API блокуються браузером без відповідних HTTP-заголовків сервера?
**CORS (Cross-Origin Resource Sharing)** — це механізм безпеки браузера, побудований на правилі однакового походження (**Same-Origin Policy**). Походження визначається трійкою: протокол + домен + порт.  
Якщо веб-додаток (наприклад, на `http://localhost:3000`) робить AJAX/fetch запит до API на `http://localhost:8080`, браузер вважає цей запит міждоменним (Cross-Origin). Для захисту користувача від атак (наприклад, викрадення сесій чи CSRF) браузер блокує читання відповіді, якщо сервер явно не дозволив це у спеціальних заголовках:
- `Access-Control-Allow-Origin: *` (або конкретний домен клієнта);
- `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS`;
- `Access-Control-Allow-Headers: Content-Type, Authorization`.  
Для небезпечних запитів браузер попередньо надсилає перевірочний запит методом `OPTIONS` (Preflight request), на який сервер зобов'язаний повернути успішний статус без тіла (`204 No Content`) із дозволеними правилами.
